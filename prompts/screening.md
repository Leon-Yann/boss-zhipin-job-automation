### 开场白多样性规则（同批内必须满足，用于避免模板化）

1. **锚定独特职责**：每条必须围绕该 JD 最独特的一条要求/场景展开（具体平台、具体指标、具体场景），禁止"贵司岗位要求XX，与我的经历高度重合"这类泛泛对应；
2. **结构轮换**：在以下形态间轮换，相邻输出避免同型——成果型（直接抛与职责最相关的数字案例）/ 痛点回应型（点出该岗位或行业的常见痛点并给出解法）/ 洞察型（针对 JD 独特要求给出你的理解与打法）/ 价值型（一句话价值主张 + 佐证）。输出时用 `openingStyle` 字段标注形态；
3. **卖点轮换**：每条只主打 1 个卖点 + 1 个佐证，同批内避免重复使用同一组数字组合；
4. **结尾轮换**：结尾在"约谈 / 问一个与岗位强相关的开放问题 / 一个可验证的承诺"之间轮换，禁止连续多条以"期待沟通/期待详聊"收尾；
5. **长度弹性**：120-220 字，因岗位复杂度而定，不强制 200 字。

## 三、逐岗判断流程

对每个岗位依次检查：

0. **收藏岗位例外（source 为 "favorites"）**：用户已亲自挑选确认投递，**跳过本流程全部筛选**，直接生成开场白（`match` 一律 "yes"，`reason` 写"收藏直投"，`score` 给 8+，`openingStyle` 仍按多样性规则轮换）。其余来源的岗位按下面 1-5 正常判断；
1. **方向**：岗位是否属于目标岗位方向；职责是否为纯销售导向、纯客服或明显无关岗位 → 不匹配；
2. **公司**：是否命中排除关键词或"已知排除公司名单"；是否符合"公司入选标准"（小公司但行业内牛，或大公司）；
   **乙方/代运营公司判断**：若公司是电商代运营/TP/TSP/ISV 等乙方服务商——没有自有品牌、业务是承接品牌方的电商运营/投放/客服等项目、同时服务多个品牌客户——一律不匹配。判别信号：公司简介含"服务商/TP/代运营/为品牌客户提供服务"、JD 描述多品牌多客户服务、业务模式明显是接品牌方项目。**防误杀**：品牌方自营岗位的 JD 中出现"管理代运营/TP 团队"属于品牌方运营岗，不算代运营公司，不要排除。
3. **薪资**：是否达到严格档；低于严格档但高于放宽档、且职责特别匹配时，标记 relaxed；
4. **硬伤**：JD 出现需 base/外派/常驻其他城市、外包性质、明显倒班、无经验限制但职责严重不符等 → 直接不匹配；
5. **职责匹配度**：核心职责与简历经历/技能的真实契合度，给出 0-10 分与一句话理由。

## 三.5 筛选目标

- 目标是让"符合并生成开场白"的岗位达到 **{{daily_target}} 条**；输入池里有多少真实匹配就输出多少，不要人为压缩数量；
- 若全部判断完后 `matched < {{daily_target}}`，必须在 summary 中如实报告缺口和原因（如池子太小/匹配不足），不要凑数、不要放宽底线。

## 四、输出格式

严格输出一个 JSON 对象，不输出任何其他文字：

```json
{
  "jobs": [
    {
      "url": "岗位详情页URL",
      "company": "公司名",
      "jobTitle": "岗位名称",
      "salary": "薪资原文",
      "match": "yes 或 no",
      "relaxed": false,
      "score": 8,
      "reason": "一句话判断理由",
      "opening": "匹配时生成开场白；不匹配时留空字符串",
      "openingStyle": "成果型/痛点回应型/洞察型/价值型"
    }
  ],
  "summary": {
    "total": "输入岗位总数",
    "matched": "match=yes 且已生成开场白的数量",
    "target": {{daily_target}},
    "insufficient": "matched < target 时为 true"
  }
}
```

`opening` 只对 `match: "yes"` 的岗位生成，严格按"开场白话术要求 + 开场白多样性规则"执行。
